# NoMount Suite 的脚本接管兼容

## 用户现象和已有证据

v1.4.96 用户的两次独立报告均显示：轻量握手正常，完整状态以退出码 0 提前结束，没有任何输出。Shell trace 最后为加载 `common/device_font_payload_runtime.sh` 后直接 `exit 0`。

第二次报告同时包含：原文件 18,547 字节、SHA-256 `779bb3f538bfae48de0b85e1db275bd0234dac34d558ca33891a6d7671863242`，按路径读取的全文与本地原始实现逐字节一致；但 `wc -c < 文件` 返回 24。文件本身没有损坏，读取/执行方式受环境影响。报告没有直接保存该 FD 的 24 字节原文，因此不把推导当作现场字节转储。

## 对用户提供安装包的静态解析

分析用户提供的 `NoMount-Suite-v1.87-LKM-6.12-3B15AP018UY00000.zip`，不执行安装包、驱动、接管或挂载操作，也不改用户手机状态。

其 `takeover.sh` 存在以下确定逻辑：

- `nm_takeover_script_entries` 递归枚举模块目录下的 `.sh` 文件，排除标准分区目录。
- `nm_takeover_scan_script` 用 AWK 静态分析脚本里的 mount 命令；没有安全初始化条件或被判为不安全时，将该路径规划为 `suppress`。
- `nm_takeover_reconcile` 创建内容为 `#!/system/bin/sh` 加 `exit 0` 的 suppressed 文件，包含换行共 24 字节；`script-begin/add/commit` 将脚本路径映射到它，原文件不需要改写。

这解释了“文件摘要正确、按路径读取正常，但 Shell 加载提前 exit 0”的组合证据。该解析器确实把字域以下五个内部实现文件规划为 suppress，包括现场 trace 中的第一个退出点：

```text
common/device_font_dynamic_guard.sh
common/device_font_payload_runtime.sh
common/mount_self_fallback.sh
common/private_payload.sh
common/universal_mount_runtime.sh
```

这些文件包含完整的函数定义和受字域策略约束的运行入口；把整个文件替换成 exit 0 会连定义也丢掉，阻断状态、字体准备或后续调用。仅修改 JSON 解析器不能修正这条执行路径。现场接管计划、FD 原始内容和修正后手机结果仍未回传，不能把安装包分析写成新版本手机验收。

## v1.4.99 的改动

将五份实现原样移到同名 `.lib`，旧 `.sh` 路径保留为只负责加载库的兼容入口。库文件不是独立的模块开机脚本。原来按 `.sh` 枚举并解析的 NoMount Suite 1.87 不会再将库定义当成独立挂载脚本接管；五个入口本身也没有 mount 命令。

每份 `.lib` 与拆分前实现的 SHA-256 相同。兼容入口直接点入库，不使用 eval、执行外部配置、复制源码到临时目录、创建后台守护或增加哈希循环；保留原 `$0` 和位置参数，原 CLI 及被 source 的调用方式继续使用。缺库时明确失败，不能悄悄返回成功。支持安装阶段、运行阶段和既有离线工具的模块路径定位。

字体生成、连续可变字重、防裁切、源变化检查、挂载提供者选择、当前启动验证、命名空间验证、输出校验、回滚条件和开机保护的实际实现均保留。没有清除 NoMount 全局规则、关闭驱动、修改其 blocklist/skip_mount 或隐藏策略，也没有在读取失败时切换挂载模式。

五份库登记到模块打包清单。既有离线检查脚本的语法清单与已有测试夹具的依赖复制同步增加 `.lib`；没有新增或运行测试套件。

## 如何更新

需要刷入完整新模块并**完整重启一次**，让 NoMount 按新模块文件重新建立原生脚本接管计划；单装 APK 不能更新这些库。不要手工清空 NoMount 的脚本规则、卸载全局规则或删除字体数据。

这是针对用户提供的 NoMount Suite 1.87 行为的兼容，不是对未来不同扫描算法的无限保证。其他 Root 管理器沿用相同入口与实现，但仍需各自设备验收。
