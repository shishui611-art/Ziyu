# v1.4.93 可变字体防裁切大小与处理链整理

## 改动依据

用户手机 v1.4.92 上次开启防裁切的记录显示，主要中文为原来源的 82.85%，部分其他位置为 70.22%–81.70%。这些比例针对导入字体，不能当作与原厂观感的逐字对比。完整可变边界为 y=-383…1215，先前用它限制每个位置，造成整体缩小且不同位置大小不一致。

仅对已有诊断副本做只读字体数据检查：来源与原厂中文快照的基本汉字默认边界均为 -100…861。来源 SHA-256 为 `77f6d84ce33f58b986d0b29834dab6ce2f179b7cdfaf5fb220ee5f06598dd4b1`。默认边界本身不能证明连续字重、实际字形大小或裁切验收通过。

## 执行路径

1. `font_clipping_variable.envelope` 仍测量全字形、IUP、组合组件与全部连续变化支持区域；不实例化、固定或离散字重。`inspect_source` 在已经得到的字形边界上聚合基本中文、ASCII 字母/数字、常用中英文标点、假名与韩文范围。该范围是大小决策规则，不是替换用户指定的验收语料。
2. 原厂 glyf 全边界与文字范围在一次头部读取中完成，缓存身份包含文件、glyf/loca/cmap/maxp/post，避免 TTC 的不同映射共用错误结果。没有可测范围或非 glyf 原厂字体回退到原全边界策略。
3. 对双方都有的范围，来源使用连续可变边界，目标使用系统所选 hhea/Typo 行框并容纳该范围原本已有的墨迹。仅在超界时计算缩小比例，无硬编码的最小/最大百分比、不放大源字体、不写系统字号或 DPI。范围外符号不再控制整体比例。
4. `prepare_templates` 为同一批次同一来源字面取满足所有目标范围的一个 UPEM，所有目标共用此比例；目标各自保留原厂行高换算。ColorOS 已有共享准备直接使用新规则；通用 `font_clipping_stage` 先收集并核验目标，再调用 `SlotCompat.prepare_clipping_batch`。单独调用 `fit_container` 时，共用范围仅限该次提供的目标集合。
5. 不重写原始 glyf/gvar/hmtx/布局与轴表。仍核验全表清单、各不变表 SHA-256、UPEM、原厂行高、完整字形 head 边界、范围适配结果、源/原厂身份和 TTC 合并。完整边界继续保留；报告另列 `referenceLimits`、`sizingPolicy`、`allGlyphsFit`，不把普通文字适配冒充所有字符防裁切通过。原 MVAR 原厂行高策略和 DSIG 处理沿用 v1.4.92。
6. 相同摘要的通用来源共用测量；原厂缓存保存小型聚合结果。TTC 只保留最新一组完整轮廓图，相邻共享轮廓可复用，不累计 64 份图。保留取消检查、源变化检查、挂载验证和事务回滚。未新增运行文件，现有安全切换处理器摘要会使旧完整负载缓存失效。

## 限制与验证范围

这是日常文字大小与防裁切的折中：范围外的罕见符号、私用区、叠加标记和未编码替换字形仍完整保留，但固定高度界面可能继续裁切。范围内连续变化仍用保守区间测量；某些字体确实较大时仍会缩小。没有共同文字范围时全边界回退仍可能明显缩小，不承诺所有字体都保持 100%。静态字体原有路径不变。

本轮不运行测试套件、新版字体生成或手机安装、刷入。只执行 Python 语法编译、Android 编译和制品完整性核对。没有新版缩放百分比、同条件耗时或温度实测，不宣称实际加速或 QQ/微信字号问题已修复。

完整固定验收语料仍为 `coolapk-53620096-r1`，SHA-256 `e45b90d6244268251d69d9b95d0ae5f36df4b0174b8b6dce280236be2db30bd2`。本轮只核对原文摘要，未执行覆盖、塑形、路由、挂载或屏幕验收。诊断原件与手机状态留在忽略目录，不随包发布。
