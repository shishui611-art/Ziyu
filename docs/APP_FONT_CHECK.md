# 检查应用字体

字体已经应用，但某个 App 没有变化时，用它查看进程实际读到了哪些字体。此功能帮助查原因，不会修改目标应用、切换字体、停止应用或改变挂载。

## 怎么用

1. 打开 **设置 → 检查应用字体**，选择应用。可以按名称或包名搜索；应用关闭时也能选择。
2. 点击“打开应用”，进入文字显示异常的页面。
3. 回到字域，点击“检查字体”。

列表读取当前 Android 用户可见、具有桌面启动入口的应用，不等同于手机所有用户和所有系统组件。没有显示的目标可以在“按包名选择”中填写包名；没有启动入口的组件需要先手动打开对应页面。Root 隐藏、工作资料和系统限制仍可能影响可见性或进程读取。

“批量检查”只检查当前运行的应用；未运行的应用不会出现在批量结果里。结果详情可展开查看包名、进程数量与字体文件，普通界面只显示结论和下一步。

## 结果有什么用

| 提示 | 可以怎样处理 |
| --- | --- |
| 已读到字域字体 | 该进程读到了字域文件；部分文字仍可能使用应用自己的字体。 |
| 还在使用旧字体 | 完全退出目标 App，再重新打开；系统界面按字域提示重启后复查。 |
| 应用没有读到字域字体 | 查看字域的挂载结果，再重新打开目标 App。 |
| 可能受系统主题影响 | 核对手机设置中的主题与字体。 |
| 发现其他字体来源 | 应用内置、下载或网页字体可能不会跟随系统更换。 |
| 没有找到运行进程 | 先打开异常页面，再返回字域检查。 |
| 暂时无法检查／判断 | 核对字域 Root 权限，保持目标应用运行；字体共享内存和自绘内容可能无法归因。 |

检查到一个字体文件不能证明屏幕上所有文字都由它绘制。不要把“已读到字域字体”当成整套字库、每个字形或所有应用均已验收。

## v1.4.98 修正的实际故障

- 原桥接向 `running` / `scan` 额外传入一个空参数，Python 入口严格校验参数数量后直接返回“诊断参数无效”。改为校验后 `shift` 并原样转发 `"$@"`，单个目标和无目标命令各自使用正确参数数量。
- 原 `app_coverage` 在加载整个字体/挂载引擎之后才分发，读取列表也会经过无关的脚本加载链。现在进入桥接后即校验 Root 和动作，直接调用原有 Python 检查器，不加载字体生成或挂载引擎。
- 原界面把当前运行进程直接当成应用选择列表，只显示包名，关闭的应用无法选择；刷新还会清空选择。新列表使用 PackageManager 查询桌面入口并读取应用名称，离线排序、搜索，不为展示列表申请 Root，不批量加载应用图标。
- Manifest 声明 MAIN / LAUNCHER 查询范围，使用 Android 的包可见性接口，不申请 QUERY_ALL_PACKAGES。依据：[Android 包可见性文档](https://developer.android.com/training/package-visibility/declaring)。
- 单独检查先用 pidof / ps 定位所选包，再核对 cmdline；不再先受全局前 96 个应用的列表限制。PID + 进程启动时间的前后验证、目标命名空间、文件来源检查及字体负载代际复查均保留。
- 批量读取保留限制，优先读取高 PID 范围；读取失败不再悄悄变成空列表。所选应用与批量的结果超时均为 25 秒，匹配后端 22 秒命令预算，避免原先单应用 10 秒超时早于后端预算。
- 界面返回取消会取消当前请求，不吞掉协程取消，不自动重跑检查或字体操作；未完整返回的 JSON 保留失败原因和退出码。

## 资源范围与限制

全局目录枚举最多 16,384 项，cmdline 最多读取 1,024 个；批量最多 24 个应用、每应用最多 3 个进程，检查阶段预算 16 秒，整个命令预算 22 秒，JSON 最多 24 KiB。pidof 独立限时 1 秒、输出 4 KiB；ps 独立限时 2 秒、输出 1 MiB，输出在读取过程中受限，超时或超量只清理本次启动的命令。ps 不支持或不可用时，使用有上限的 /proc 兼容路径；范围受限会标记结果不完整。

这不是对所有 Root 隐藏策略和 ROM 的绕过方案。共享内存、自带字体、自绘文字、PID 退出或复用、源代际变化仍可能导致无法判断。没有同条件实测，不宣称检查或字体切换已经达到特定加速比例。
