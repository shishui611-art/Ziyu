# 模块连接与 Root 回复修正

## 证据与边界

用户反馈首页停在“等待模块连接 / 未收到 JSON 数据”，使用 NoMount Suite LKM 1.87。已静态核对用户提供的 ZIP、脚本和 DEX，尚未取得故障手机的命令退出码、stdout、stderr 与隐藏作用域配置。因此不能断言 NoMount 篡改了 su 输出，也不能用另一台手机正常工作来宣称该用户故障已消失。

本轮修正源码中已经确认的执行缺陷：

- 旧 RootShell 在请求进程结束后只用 available() 再读一次就关闭管道，不能证明回复已收完整；子进程继承管道又使无限等待 EOF 不可行。
- 旧首次握手只接受单行 JSON；解析失败被吞掉，随后继续加载较重的完整状态。BOM、前置提示、格式化 JSON 和缺失回复混成同一条错误。
- 旧状态解析失败会新建默认快照，把未读取状态当成默认字体；部分分支仍继续读取附加信息并预热字体。

## 实际改动

1. 每条 App Root 请求使用随机 UUID 的开始/结束标记。命令放在子 shell 内，原有 exec、exit、set -e 不会跳过外层完成标记。stdout 与 stderr 分别发出原命令退出码，必须两份一致才认为回复完整。标记不写入日常返回正文；不执行第二遍命令。
2. 两路输出仍交替、有上限地读取。进程退出后不将 available()==0 当作完成，继续等待标记；无新数据的退出宽限最多 300 ms，仍受原请求总超时限制。成功收到完整回复即结束，不等待继承管道的后台进程退出；没有新增常驻线程、守护进程或 RootService。
3. 接受两路被 su 合并及 LF/CRLF；标记跨块匹配仅保留短尾，UTF-8 只在完整回复组装时解码。每路上限 32 MiB，避免无限日志增长；该上限针对文本桥输出，不是字体导入文件大小。返回真实的命令退出码，超时、缺失结束标记、权限拒绝不能作为成功。
4. 首次连接直接调用 app_handshake.sh probe-v2，只读模块元信息与本次启动身份，使用固定键值字段；路径正规化后核对 UID、模块 id、目录、版本和组件，App 在内存中构造类型明确的对象。旧 probe 与 JSON 握手保留，新 App 可读取旧 JSON 模块；已知缺少握手组件的旧模块才进入已有状态兼容路径，不对未知坏回复静默加载完整状态。
5. 完整状态与现行 ViewModel JSON 入口支持前置文本、BOM、多行对象、字符串转义与括号；优先完整状态对象。JSON 缺失或非法仍失败，不能跳过验证。
6. 状态失败保留上次确认的字体、版本和事务信息，首次未读取显示“尚未读取”，不伪造恢复默认或挂载成功。读取出错时暂停附加读取与字体预热；错误中保留 stderr、结构化原因或退出码。快速握手不作为字体挂载验收。

没有修改 NoMount 隐藏列表、Root 授权或应用可见性配置，没有切换挂载模式、全局卸载或重试字体写入。Root 被拒绝、模块目录被隐藏、桥脚本不存在、脚本本身失败等，仍须按真实原因处理；本修正不保证穿透这些限制。

- Android 编译、vital lint、Shell/Python 语法与包清单/签名/摘要核验单独记录；未运行测试套件。
- 未安装、刷入或重启，暂无新握手在故障 NoMount 手机的运行证据。管道分片、合并、CRLF、旧版模块、超时/取消及真实字体操作仍待设备验收，不能从编译通过推断已覆盖。

- 字库基准为完整 coolapk-53620096-r1，SHA-256 e45b90d6244268251d69d9b95d0ae5f36df4b0174b8b6dce280236be2db30bd2；本轮未做字库、字体生成、路由、挂载或屏幕验收，也不声称切换加速。

API 依据：[Android InputStream.available](https://developer.android.com/reference/java/io/InputStream#available())。available 是可立即读取的估计值，不是消息完成协议。本轮用显式回复边界修正判定，不以新增错误文案代替修正。
