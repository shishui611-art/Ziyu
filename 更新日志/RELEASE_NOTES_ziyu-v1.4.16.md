# ziyu v1.4.16 — 组合字体原厂 CJK 集合共享字形修复（本地 Debug 候选）

用户手机 v1.4.10 日志中的组合字体（中文/英文取幼圆、数字取数字新）切换在兼容路径失败：逐面生成原厂 NotoSansCJK 集合时报告

```
[MIX] CJK 集合生成失败：原厂共享字形 U+00A0 对应不同来源轮廓，不能安全覆盖
```

随后 `stage=100` 报「组合字体原厂集合逐面生成或契约校验失败」，本次切换整体未生效。

## 原因

- 本机原厂 NotoSansCJK 原厂集合把 U+0020 与 U+00A0 映射到同一个原厂字形（只有一个宽度）；同类还有 U+002D/U+00AD/U+2011、U+00B7/U+2022/U+2027/U+30FB、U+2003/U+3000、部分部首与统一汉字等别名组，均共用单个原厂字形。
- 组合来源（幼圆）为这些字符提供不同字形或不同宽度：U+0020 为 `space`（341/1024）、U+00A0 为 `uni00A0`（287/1024）。一个原厂槽位无法同时容纳两个不同的来源字形。
- 原实现把这种无法满足的共享字形映射当成致命错误，直接中止整个集合生成；本机其他可替换字体槽位的成果也一并作废。

## 修正

- `common/composite_collection_build.py`：遇到共享字形冲突时保留该原厂槽位，并把槽位与字符记录到逐面证明（`retainedSharedConflictSlots`、`retainedSharedConflicts`），不再中止整个集合；其余可安全替换的中文、拉丁和数字字形继续替换。
- 原有安全契约保持不变：原厂 cmap/UVS、字形索引、GSUB/GPOS/GDEF、name、OS/2、hhea/vhea/vmtx/VORG 等布局与度量契约逐面校验；输出哈希、组合来源哈希、源文件变化检查、逐面证明与回滚条件不变。
- 日志中另一条「文本目标包含无效动作：/system/fonts/NotoSansHanifiRohingya-Regular.otf」是 v1.4.10 的通用计划校验问题，v1.4.11 已修正，本版包含该修正。

## 本地验证

- 使用用户提供的 `幼圆.ttf`（upem 1024）与 `数字新.ttf`（DSEG7 Classic，upem 1000）按手机管线生成组合字体；再用同族 Noto Sans CJK CFF/CID 原厂集合（head/hhea 数值与诊断中的原厂快照一致，fontTools 4.63.0 与模块内置运行时相同）复现出与手机日志完全相同的错误。
- 修正后在同一字体组合上完成逐面生成：可安全替换的 CJK 约 3.0 万字、拉丁与数字继续替换；共享字形冲突槽位保留原厂并记录（单面示例 407 个共享槽位，其中多数为部首、兼容汉字与标点别名）。
- 逐面契约校验通过：`protected()` 记录的原厂布局契约在生成前后一致，输出集合的字形索引、cmap、字符映射与垂直度量未变化；集合面数量与原厂一致。
- 未在手机安装、刷入、重启或做应用显示对照验收；未测量手机端集合逐面编译耗时与 360 秒任务超时的余量，也未验证冲突槽位在具体应用中的显示效果。编译与本地字体编译验证不等于完成真机验收。

## 适用范围与限制

- 本版只改变「无法同时满足的共享字形」处理方式，不改变挂载方式、字重策略、字形覆盖范围或回滚条件。
- 共享槽位保留原厂意味着这些别名字符仍显示原厂字形；如需全部替换，需要来源字体与原厂共享关系一致，或后续提供逐字符选择方案。
- 组合字体切换仍需准备下一启动负载并重启生效；失败时保留上一套可用负载。
