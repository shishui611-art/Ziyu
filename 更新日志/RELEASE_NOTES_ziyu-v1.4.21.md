# ziyu v1.4.21（本地 Debug 候选）

本版针对 v1.4.20 设备日志里“ColorOS 已生成，但 CJK 集合生成期间被 360 秒时限终止”的执行路径。

- Shell 与 Python 监督器共用单调运行时钟，设备休眠不消耗计算预算。监督器原子发布每秒时间样本，Shell 读取同一任务专属文件，任务收尾删除。
- 普通路径仍为 360 秒。明确进入原厂 CJK 集合生成后，允许一次 360 秒追加预算，默认总计最多 720 秒；外层监督器最多 735 秒运行时间，保留取消和有界清理。自定义运行时限仍有 900 秒上限。
- 集合生成显示为 88%“正在生成原厂 CJK 字体集合”，其后的验证显示为 90%“正在核验字体负载与原厂布局契约”，不再把整个集合生成隐藏在 86% 校验阶段。
- 前台字体服务在任务进行时持有 PARTIAL_WAKE_LOCK，最长 16 分钟，完成、取消、系统超时或服务结束时释放。只有服务正常启动时这项保活生效；服务被系统拒绝或杀死时，Root 任务仍受监督器管理。
- v1.4.20 的跨槽位来源复用保留，原厂契约、源变化、输出哈希、最终校验、挂载验证与回滚条件不删减。

## 证据与限制

旧版实机任务 1792933404-2132：ColorOS 阶段打印 11 个槽位、9 个生成结果和 152.887 秒批处理计时；随后 CJK 集合编译收到 signal 15，总任务 rc=124。Shell elapsed=360，监督器 durationSeconds=201.292；这与两个计时源对休眠的处理差异吻合，不代表全部延迟已得到归因。

旧版任务 1792934141-7889 的 ColorOS 批处理打印 142.832 秒，随后原厂五面集合生成已输出 PASS，但在后续验证完成前仍被 360 秒总时限终止（监督器 361.755 秒）。这证明总预算本身也不足，不能只归因于休眠。以上均为旧版用户发起任务的只读观察，不是本版验收。

本次只做编译与包完整性检查，不自行运行行为或性能测试。未自动安装、刷入、应用字体或重启，手机应用是否完成与屏幕关闭后的稳定性尚待验证。APK 使用既有 Debug 签名，不等于正式签名发布；不上传云端。
